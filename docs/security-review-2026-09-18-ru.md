# Review OneLayer — 18 сентября 2026

Объект: текущий рабочий проект на базе `3b93cd9`, включая API, verifier, on-chain код, криптографические пакеты, backup/recovery, deployment и тесты. Существующий незакоммиченный `docs/project-overview-ru.md` не изменялся. Это review исходников и локальных проверок, не аудит развернутой инфраструктуры и не доказательство отсутствия других уязвимостей.

Вывод: криптографический каркас полезен, но текущий MVP нельзя считать надежной системой подтверждения актуальных прав или аварийного восстановления. Главные разрывы находятся на границах доверия verifier, полноте incident index и реализации backup/recovery. Корректность Merkle proof сама по себе их не закрывает.

Приоритеты: P0 — возможность ложного доверенного результата, блокирует использование для значимых решений; P1 — существенная потеря защиты/доступности; P2 — эксплуатационная надежность. Ниже Standards и Spec разделены; нумерация служит ссылкой, а не количеством независимых способов атаки.

## Standards: реализация и документированные границы

### S1. P1 — обещанная loopback-граница не реализована

`apps/demo-api/src/main.ts:517`, `apps/verifier/src/main.ts:28`: оба сервиса слушают `0.0.0.0`. Launcher `deploy/devnet-demo/native:201` не меняет bind API/verifier; loopback HOSTNAME задан только web. Это противоречит README и ADR-0006.

Сценарий: при отсутствии внешнего firewall клиент из доступной сети обращается непосредственно к API/verifier. Package/metadata/QR routes не требуют admin session. URL с localhost и CORS не ограничивают такой доступ.

Исправление: bind `127.0.0.1` по умолчанию для demo; проверить реальные listening sockets. Для production — единственный private ingress с device authentication и server-side session/RBAC на раскрытие данных, закрытые upstream-порты. Сам факт отсутствия production VPN в demo не является дефектом; дефект — нарушение заявленного локального bind.

### S2. P1 — FINALIZED snapshot не доказывает соответствие данных anchor

`apps/demo-api/src/admin.ts:1383`, `:1567`, `:1587`: snapshot шифрует текущее содержимое, но получает root из таблицы `demo_anchor`. Признак FINALIZED зависит от наличия этой строки и отсутствия локального incident. Пересчета root содержимого нет. `:1915` проверяет структуру plaintext, затем считает элементы массивов. Это слабее определения Finalized Snapshot в CONTEXT и ADR-0005.

Сценарий: records изменили напрямую либо штатно изменили после предыдущего anchor; новый backup получает старый root и статус FINALIZED. AEAD доказывает сохранность именно зашифрованного payload, но не его соответствие опубликованному состоянию. Recovery сравнивает метаданные, а не самостоятельно вычисленное доказательство содержимого.

Исправление: согласованный срез состояния; пересчет commitments и проверка выбранного finalized anchor непосредственно через доверенный chain reader; свежий полный incident index. Полный рабочий state содержит больше, чем records одного batch: ему нужен отдельный проверяемый manifest/hash с привязкой к anchor. Нельзя объявлять один batch root доказательством всех таблиц и истории.

### S3. P1 — пять Backup Centers зависят от одной PostgreSQL

`apps/demo-api/src/admin.ts:1038`, `:1614`: центры создаются как метаданные, ciphertext replicas пишутся в ту же БД. Отдельные имена volumes/credentials не создают хранилища. Это не выполняет даже локальные отдельные volumes/credentials из ADR-0005.

Сценарий: потеря PostgreSQL/диска или привилегированное удаление уничтожают одновременно рабочие данные и все пять копий.

Исправление: реальные storage adapters, независимые права доступа, чтение записанного ciphertext перед COPIED; отдельный recovery catalog, доступный без основной БД. Географическая независимость остается явно отложенной production-задачей.

### S4. P1 — recovery keys не переживают restart

`apps/demo-api/src/main.ts:48`: KEK, пять shares и approval private key создаются заново при запуске. `context.recoveryShares` передается в context, но путь выдачи долей хранителям не реализован.

Сценарий: после перезапуска старые ciphertext остаются, а прежнего ключевого материала в текущем приложении уже нет. Даже до restart пользователь не получает предусмотренный механизм custody provisioning. Наличие функции Shamir не означает готового recovery процесса.

Исправление: provisioning и подтвержденная доставка долей независимым хранителям; устойчивые версии ключей, защищенная custody writer key, политика ротации. Проверка обязательна после остановки процесса и на чистом host. Chief Admin approval — отдельный контроль, не четвертая доля и не криптографический запрет расшифрования для обладателя KEK.

### S5. P2 — выбранная replica не является источником restore

`apps/demo-api/src/admin.ts:1858`, `:1877`: загрузка читает `snapshot.encrypted_package`, а выбранный центр используется для метаданных.

Сценарий: центральный ciphertext поврежден, replica исправна — recovery все равно берет поврежденный центральный пакет. Повреждение bytes выбранной replica может остаться незамеченным.

Исправление: читать ciphertext из выбранного storage adapter и проверять именно его; тестировать восстановление при недоступной основной БД и отказе отдельных центров.

### S6. P2 — retention не ограничивает весь объем backup

`apps/demo-api/src/admin.ts:1452`: удаляются replica rows, но исходные полные `snapshot.encrypted_package` остаются.

Сценарий: UI показывает максимум 12 папок на центр, однако повторные backups продолжают увеличивать БД до исчерпания диска.

Исправление: GC неиспользуемых envelopes с учетом retention и active recovery; квоты и контроль свободного места. Сохранение единственной доверенной копии — обязательный инвариант GC.

### S7. P2 — snapshot не является гарантированно единым срезом

`apps/demo-api/src/admin.ts:1542`, `:1248`: обычный BEGIN и серия SELECT при READ COMMITTED. Параллельная публикация/изменение может быть видна только части запросов.

Сценарий: records, versions, certificates и anchors в snapshot относятся к разным моментам. Шифрование сохраняет это внутренне несогласованное состояние без ошибок.

Исправление: REPEATABLE READ и определенная граница публикации; проверка ссылочной целостности и конкурентный тест capture/publish.

Эвристика сопровождения: `apps/demo-api/src/admin.ts` объединяет records, publication, backup и recovery примерно в 2700 строках — possible Divergent Change. Выделить модули по инвариантам полезно после исправления доверия и восстановления; само по себе это не уязвимость.

## Spec: что проверяется и чего гарантии пока не обеспечивают

### F1. P0 — нет закрепленного доверия к issuer/program/registry segment

`packages/canonical-ts/src/index.ts:563` проверяет подпись ключом из самого certificate package. `apps/verifier/src/verify.ts:304` не добавляет проверку разрешенного issuer. `apps/verifier/src/solana-rpc.ts:58` и `:79` выбирают program ID из package; при derivation ledger PDA используется `segment.registry` без сравнения с ожидаемым config PDA для registry сертификата.

Подтверждено локальной проверкой с mock chain: взять корректные доказанные поля, изменить certificate ID, issuerKeyId и issuedAt, переподписать другим ключом — результат VERIFIED. При неизвестном новом ID lifecycle возвращает null, что не снимает VERIFIED. Это не позволяет незаметно изменить поля под прежним root, но позволяет подделывать идентичность issuer и метаданные, обходить привязку lifecycle к исходному ID.

Дополнительная граница по коду: принадлежность ledger нужному registry не доказана; отсутствие pin program ID позволяет package выбирать источник доверия. Проверки owner/PDA относительно выбранной атакующим программы не заменяют trust policy. Полный live-chain сценарий этой ветви не выполнялся.

Исправление: конфигурация доверия вне package — cluster/genesis, program ID, registry config PDA, разрешенные issuer keys и их периоды/отзыв. Проверять `segment.registry == expectedConfigPda`. Добавить отрицательные тесты чужого issuer, program и registry, сохранив проверку легальной ротации ключей.

### F2. P1 — incident log не аутентифицирует программу-источник

`apps/demo-api/src/incident-events.ts:82`, `apps/demo-api/src/incident-index.ts:101`: parser принимает подходящий `Program data:` по discriminator и registry bytes без проверки invocation stack/program ID.

Сценарий: посторонняя программа в транзакции, упоминающей registry account, выпускает похожее событие. Само упоминание account не доказывает авторство события. Индекс может отразить чужое событие как открытие/закрытие настоящего incident.

Исправление: проверять активную программу по invocation stack, включая CPI; сверять итоговое состояние IncidentNotice PDA через finalized чтение. Отрицательный тест — подходящий payload от другой программы. Live-chain эксплуатация не выполнялась.

### F3. P1 — после 100 транзакций индекс может пропустить incident навсегда

`apps/demo-api/src/solana-rpc.ts:14`, `:47`: читается одна страница из 100 signatures без pagination. `apps/demo-api/src/incident-index.ts:112` затем продвигает watermark до head.

Сценарий: между сканированиями прошло более 100 транзакций либо индекс запускается на длинной истории. Более старое открытие incident не попадает в выборку; индекс заявляет полноту и следующие проходы его не догоняют. Verifier может считать чистым спорный batch.

Исправление: pagination до сохраненного cursor/подтвержденного начала истории; watermark продвигается только после доказанно полного диапазона. Gap, недоступная история и усеченные logs должны давать STALE/UNAVAILABLE. Тесты: 101+ событий, несколько страниц, сбой посредине, restart.

### F4. P1 — неизвестная актуальность сохраняет VERIFIED

`apps/verifier/src/verify.ts:250`: null/error lifecycle оставляет status и добавляет только CURRENT_STATUS_UNAVAILABLE. Это поведение явно закреплено существующим тестом, то есть вопрос также в продуктовом контракте.

Сценарий: сертификат уже отозван/заменен, но endpoint актуальности недоступен; историческое включение в anchor продолжает давать VERIFIED. В связке с F1 новый ID гарантированно не находится в lifecycle.

Исправление: отдельные результаты «историческое включение доказано» и «актуальность подтверждена». При неизвестной актуальности запрещать положительный результат для текущих прав. Lifecycle должен быть независимо проверяемым: сейчас это HTTP-ответ той же системы/БД, которую предполагается контролировать.

Дополнительная неоднозначность: `incident-index.ts:81` теряет различие CONFIRMED/FALSE_POSITIVE/RESOLVED из on-chain status; `incident-store.ts:65` сводит их к RESOLVED. Уточнить политику подтвержденного нарушения: подтверждение факта не должно автоматически означать пригодность прежних данных. Нужны отдельные состояния и тесты, а не только флаг OPEN.

### F5. P1 для аварийного применения — RESTORED пока является демонстрацией

`apps/demo-api/src/admin.ts:2377`: restore записывает hashes и summary в `recovery_restore_target`, выставляет RESTORED и очищает plaintext. Рабочие records/versions/certificates в целевую систему не импортируются.

Сценарий: исходные данные утрачены, flow завершился успешно — рабочего реестра после него нет. ADR-0005 и MVP plan откладывают настоящий restore drill: это известная граница MVP, которую нельзя представлять как реализованную аварийную защиту.

Исправление: полноценный импорт в изолированную чистую target DB, восстановление необходимых ключевых ссылок/состояний, проверка roots/связей, проверка обслуживания старого QR и дальнейшей публикации, затем управляемое переключение. До этого UI/result должны явно обозначать проверку recovery, а не завершенное восстановление реестра.

## Сценарии

| Сценарий | Что дает текущий проект | Что требуется дополнительно |
|---|---|---|
| Изменили раскрытое поле в уже выданном package | Signature и Merkle checks обнаруживают изменение относительно прежнего anchor | Закрепить trust policy F1 |
| Повредили encrypted snapshot/chunk | AEAD/hash checks обнаруживают повреждение | Реальная независимая исправная replica и доступные recovery shares |
| Оператор без нужной роли вызывает защищенную admin-операцию | Есть sessions, RBAC и CSRF; соответствующие тесты проходят | Production identity/device perimeter и защита секретов |
| Неподтвержденный anchor, paused registry, устаревший индекс | Есть fail-closed проверки этих состояний | Исправить ложную полноту индекса F2/F3 |
| Прямо изменили рабочую БД | Прежний package продолжает доказывать старую версию; отдельный reconcile может найти расхождение | Независимый непрерывный монитор и доверенный chain root; текущий `main.ts:234` сверяет с root из той же БД и вызывается через internal endpoint |
| Авторизованный сотрудник ввел ложные данные до anchor | Ложные данные могут быть корректно зафиксированы | Внешние основания, maker-checker, независимая авторизация изменения |
| Предъявили старый certificate | Историческое включение сохраняется; при рабочем lifecycle есть historical/superseded статусы | Независимая проверка актуальности и отказ при ее недоступности |
| Скомпрометировали процесс API/host | В одном процессе доступны issuer secret, writer KEK и shares | Разделение ролей и процессов, защищенная custody, минимальные полномочия |
| Потеряли БД/host или перезапустили API | Существующая recovery демонстрация не обеспечивает восстановление | S3–S5, F5 и проверка на чистой среде |
| Недоступны RPC/package service/БД | Значительная часть проверок становится недоступной | Репликация off-chain artifacts, резервные RPC, измеренные RTO/RPO |
| Скопировали QR | QR связывает package и hash, не подтверждает личность предъявителя или право распоряжения | Проверка личности и полномочий в бизнес-процессе |
| Украли governance/upgrade authority | Права этой authority находятся вне защиты Merkle proofs | Отдельная governance policy, multisig/timelock, контроль upgrade authority; фактическое развертывание здесь не проверялось |

Blockchain хранит commitment, а не полный рабочий реестр. Утраченное содержимое невозможно восстановить из одного root. Три доли обеспечивают возможность получения ключа, а не доступность ciphertext. Пять копий в одном failure domain не равны пяти независимым центрам.

## Порядок исправлений и acceptance

1. Закрыть S1 и F1: доверенные issuer/program/registry, loopback bind, отрицательные проверки чужой идентичности. До этого не использовать VERIFIED для решений о правах.
2. Исправить F2/F3/F4 и определить семантику подтвержденных incidents. Проверить длинную историю, чужие logs, unavailable lifecycle и rollback локальной БД.
3. Реализовать S2–S5 и F5: реальные storage/custody, consistent snapshot, проверяемый full-state manifest, restore на чистой среде после потери основной БД и restart.
4. Закрыть S6/S7, вынести самостоятельные модули, провести fault injection: потеря двух центров/двух долей, corrupted replica, disk full, сбой посреди capture/restore.
5. Перед production отдельно проверить identity, device perimeter, key/governance custody, RPC trust/availability и измеренные RTO/RPO. Это не закрывается browser demo.

- Локальное негативное воспроизведение F1 с mock chain показало VERIFIED после смены issuer/ID/issuedAt и собственной подписи. Это не подтверждение эксплуатации развернутого devnet endpoint.
- Browser/live-devnet smoke, нагрузочные проверки, аудит зависимостей по актуальным CVE и проверка фактического firewall/upgrade authority не выполнялись. Production secrets не извлекались; боевые данные не менялись.

Итого по осям: Standards — 7 конкретных проблем плюс одна архитектурная эвристика; наиболее серьезная — ложная привязка snapshot к finalized root. Spec — 5 групп проблем/ограничений; наиболее серьезная — отсутствие независимого trust policy verifier. Прохождение существующих тестов не опровергает эти выводы: часть проблем закреплена текущим тестовым контрактом, часть находится вне покрытия.
