# OneLayer — сценарии использования

**Статус:** описательный документ, 2026-08-04. Нормативной силы не имеет.
**Область:** визуальный MVP Gate C (`IMPLEMENTATION_PLAN.md` §5.4), devnet, synthetic-данные, test keys.
**Связанные документы:** `docs/presentation-ru.md` (разбор для презентации), `docs/adr/0003-visual-mvp-boundaries.md` (границы реализации), `docs/adr/0004-certificate-data-boundary.md`, `docs/adr/0005-mvp-backup-centers-and-recovery.md`.

Каждый сценарий описан как: актор → предусловия → шаги → результат → отказы. «Экран» означает адрес в `apps/mvp-web`, «API» — маршрут `apps/demo-api`.

---

## 1. Акторы

| Актор | Кто это в реальной организации | Что даёт ему систему | Где он работает |
|---|---|---|---|
| `operator` | сотрудник реестра, который вносит и публикует изменения | демо-логин + браузерный test wallet с ролью оператора on-chain | Admin-панель |
| `auditor` | внутренний контролёр, ревизор, представитель надзора | демо-логин без права мутаций | Admin-панель, read-only |
| `chief_admin` | глава, который разрешает восстановление | отдельная асимметричная подпись `Approve restore` | Admin-панель, только recovery approval |
| governance authority | руководитель реестра (условно «глава кадастра») | отдельный ключ; в Gate E — мультисиг + timelock | CLI/guarded операции, не браузер |
| emergency authority | дежурный по безопасности | отдельный ключ, только `pause_registry` | CLI/guarded операции |
| проверяющий | нотариус, банк, покупатель, любой человек с QR | публичная панель, без логина | публичная панель |
| Integrity Monitor | независимый контур (Gate D) | собственные учётные данные и независимое чтение источника | вне MVP |

В модели MVP предусмотрены `operator`, `auditor`, `chief_admin` и проверяющий. Governance/emergency присутствуют как отдельные ключи, но их операции выполняются guarded CLI, а не из UI, — это граница, а не недоделка.

## 2. Сценарии оператора

### UC-01. Внести сертификат вручную

**Актор:** `operator`. **Экран:** `/admin/records`.

**Предусловия:** активная server-side сессия с ролью `operator`; synthetic marker в БД.

**Шаги:**
1. Оператор открывает раздел записей. Форма построена из схемы `land-registry-v1`, которую отдаёт API (`GET /v1/admin/schema`), а не из констант браузера.
2. Заполняет `internalRecordId`, обязательные поля (`status`, `cadastralNumber`) и любые дополнительные.
3. Нажимает «Save record».

**Результат:** запись создана или получила новую версию; открывается карточка записи с `recordIdCommitment`, `fieldRoot`, `recordCommitment`, batch leaf и `field_commitment` каждого пути.

**Отказы:** значение вне перечня (`FIELD_VALUE_NOT_ALLOWED`), decimal с чужим scale (`FIELD_DECIMAL_INVALID`), timestamp с дробной частью (`FIELD_TIMESTAMP_INVALID`), отсутствие обязательного поля (`FIELD_REQUIRED_MISSING`). Роль `auditor` получает `ROLE_FORBIDDEN` на уровне API, а не скрытием кнопки.

### UC-02. Импортировать сертификаты пачкой (JSON или CSV)

**Актор:** `operator`. **Экран:** `/admin/records`, блок импорта. **API:** `POST /v1/admin/records/import`.

**Шаги:**
1. Оператор выбирает формат: JSON (объект или массив объектов) или CSV (первая строка — пути полей).
2. Вставляет содержимое и нажимает «Validate (dry run)».
3. Читает отчёт: принятые строки с каноническими значениями и отклонённые строки с номером строки, кодом и путём.
4. Исправляет источник и нажимает «Import».

**Результат:** приняты только валидные строки; каждая создаёт запись или новую версию существующей. Записи помечены `origin='ADMIN_UI'`.

**Отказы:** поле вне схемы отклоняет строку с `CANONICALIZATION_FAILED` и указанием пути; дубликат `internalRecordId` внутри одного файла — `RECORD_DUPLICATED`; несовпадение числа колонок — `CSV_COLUMN_COUNT_MISMATCH`.

**Важно:** dry-run ничего не пишет. Commitments в нём не показываются: `field_salt` выводится из ключа поля, который создаётся вместе с версией записи, поэтому «предварительный» commitment не был бы равен итоговому.

### UC-03. Посмотреть каноническое состояние перед публикацией

**Актор:** `operator` или `auditor`. **Экран:** `/admin/records`, блок canonical preview.

**Шаги:** оператор смотрит следующий `batchSequence`, число листьев, `merkleRoot`, `manifestHash`, `previousAnchorHash` и построчно — commitments каждой записи.

**Результат:** оператор видит ровно те значения, которые попадут в транзакцию. `certificateHash` здесь отсутствует намеренно: он появляется только после finalized anchor и выдачи пакета.

### UC-04. Опубликовать batch в Solana devnet

**Актор:** `operator`. **Экран:** `/admin/publish`.

**Предусловия:** реестр инициализирован, роль оператора выдана guarded-операцией, в браузере доступен Wallet Standard кошелёк с devnet-аккаунтом, на нём есть SOL на комиссию.

**Шаги:**
1. «Connect wallet» — подключается только `solana:devnet` аккаунт.
2. «Prepare and simulate» — сервер собирает batch, фиксирует `intentHash`, idempotency key и срок действия blockhash, симулирует транзакцию.
3. Оператор читает review: cluster, program ID, инструкция, все аккаунты с флагами signer/writable, registry config, role PDA, segment PDA, batch sequence, `merkleRoot`, `manifestHash`, `previousAnchorHash`, fee payer, blockhash, логи симуляции.
4. «Review complete — request wallet signature» — кошелёк подписывает **точно те байты**, что были показаны.
5. «Check finalization» — статус доходит до `FINALIZED`.

**Результат:** anchor опубликован; в БД появляется finalized batch с сигнатурой и слотом.

**Отказы:** неуспешная симуляция оставляет состояние `SIMULATION_FAILED` и не предлагает подпись; отказ в кошельке → `SIGNING_REJECTED`; истёкший blockhash → `EXPIRED` и возврат к подготовке; неизвестный ответ RPC → `UNKNOWN`, который разрешается опросом **известной** сигнатуры, а не пересборкой транзакции. Повторный клик и reload используют тот же idempotency key и не создают второй batch.

### UC-05. Выдать сертификат с полным раскрытием

**Актор:** `operator`. **Экран:** `/admin/publish`, блок выдачи (доступен только в состоянии `FINALIZED`).

**Шаги:** выбрать запись → оставить все поля отмеченными → «Issue certificate package».

**Результат:** подписанный `CertificatePackageV1`, `certificateHash`, QR (SVG/PNG), ссылка на публичную страницу и на Solana Explorer. Предыдущий сертификат той же записи получает статус `SUPERSEDED`.

**Отказы:** попытка выдать до `finalized` → `ANCHOR_NOT_FINALIZED`; если on-chain
registry paused или его config недоступен, выдача QR блокируется (`REGISTRY_PAUSED`
или fail-closed).

### UC-06. Выдать сертификат с частичным раскрытием

**Актор:** `operator`. **Экран:** тот же блок.

**Шаги:** снять отметки с полей, которые раскрывать не нужно; сводка меняется на `SELECTIVE_FIELDS`; выдать пакет.

**Результат:** пакет содержит значения, соли и field proof **только** выбранных путей. `fieldRoot`, batch proof и anchor те же, что при полном раскрытии той же версии записи, поэтому проверка даёт `VERIFIED`.

**Пример:** банку показывается `status` и `areaSquareMeters`, но не `holderCommitment` и не `cadastralNumber`.

**Граница:** число листьев field-дерева видно из proof — скрыты значения, а не факт существования полей.

### UC-07. Посмотреть выданные сертификаты и получить QR-артефакт

**Актор:** `operator` или `auditor`. **Экран:** `/admin/certificates`.

**Шаги:** открыть список → выбрать сертификат → посмотреть режим раскрытия, `certificateHash`, batch, `merkleRoot`, slot, сигнатуру; скачать QR в SVG или PNG; открыть публичную страницу или Explorer.

**Результат:** артефакт для печати, письма или слайда, пока registry находится в
рабочем состоянии (`RegistryConfig.paused = false`).

### UC-08. Проверить журнал операций

**Актор:** `auditor`. **Экран:** `/admin/timeline`.

**Шаги:** просмотреть append-only ленту: кто, когда, какое событие (`RECORD_UPSERTED`, `RECORDS_IMPORTED`, `BATCH_SIMULATED`, `TRANSACTION_SIGNED`, `ANCHOR_FINALIZED`, `CERTIFICATE_ISSUED`, отказы).

**Результат:** восстановимая последовательность действий. В payload — только хэши, статусы и публичные идентификаторы; секретов там нет.

**Граница:** в Gate C журнал append-only, но не имеет hash-chain — план этого и не утверждает (§2.6).

### UC-09. Увидеть состояние контура целиком

**Актор:** `operator` или `auditor`. **Экран:** `/admin`.

**Результат:** число записей и версий, сколько импортировано через UI, число сертификатов и из них частичных, открытые on-chain инциденты, последний finalized anchor с ссылкой на Explorer. Все значения — результат запросов, а не статика.

## 3. Сценарии проверяющего

### UC-10. Проверить сертификат по QR с телефона или камеры

**Актор:** проверяющий, без логина. **Экран:** `/verify` или прямая ссылка `/c/<certificateId>?h=<hash>`.

**Шаги:**
1. Сканировать QR камерой, загрузить изображение QR или вставить ссылку/пакет вручную.
2. Дождаться результата.

**Результат:** один из статусов с иконкой, текстом и объяснением: `VERIFIED`, `VERIFIED_HISTORICAL`, `SUPERSEDED`, `VERIFIED_NO_INCIDENT_CHECK`, `DISPUTED`, `INVALID`. Показываются cluster, batch, slot, состояние incident index и **раскрытые пакетом поля**.

**Отказы:** ссылка без хэша не проверяется вовсе — QR binding нечем проверить;
подменённый пакет отклоняется до обращения к цепочке (`QR_HASH_MISMATCH`);
paused registry отклоняет QR с `REGISTRY_PAUSED`.

**Граница:** камера — прогрессивное улучшение. Отказ в доступе к камере никогда не блокирует загрузку изображения и ручной ввод.

### UC-11. Понять, что именно доказано

**Актор:** проверяющий. **Экран:** `/how-it-works`.

**Результат:** объяснение, что в Solana попадает только `merkleRoot` и `manifestHash`, что QR несёт только идентификатор и хэш сертификата, что проверяется в пяти шагах и почему зелёный статус не выдаётся при непроверенной полноте incident index.

### UC-12. Столкнуться с изменёнными данными

**Актор:** проверяющий. **Предусловие:** кто-то изменил запись в БД напрямую (сценарий `demo incident`).

**Результат:** проверка того же QR даёт `DISPUTED` — открытый инцидент покрывает batch. Ложного зелёного статуса не возникает: при недоступном или отставшем индексе результат понижается до `VERIFIED_NO_INCIDENT_CHECK`.

### UC-13. Столкнуться с устаревшей версией записи

**Результат:** если запись получила новую версию после выдачи сертификата — `VERIFIED_HISTORICAL`; если сертификат заменён новым для той же записи — `SUPERSEDED`. Оба статуса означают «доказано, но не актуально», и оформлены отдельными видами результата, а не оттенком цвета.

## 4. Сценарии владельца реестра (вне браузера)

Эти операции намеренно не выведены в UI: у них другая граница доверия и отдельные подтверждения.

### UC-14. Развернуть программу и выдать роль оператора

**Актор:** governance authority. **Инструмент:** guarded CLI (`deploy/devnet-demo`).

**Шаги:** native preflight проверяет PostgreSQL/Node toolchain, devnet-only RPC, баланс test key, порты и synthetic marker → deploy программы с approval digest → `initialize_registry` → `grant_operator` для браузерного test wallet с правом `PERM_PUBLISH_ANCHOR`.

**Результат:** контур готов; браузер получает возможность публиковать, но не управлять правами.

### UC-15. Приостановить реестр

**Актор:** emergency authority. **Результат:** `pause_registry`; все публикации отклоняются с `REGISTRY_PAUSED`. Снять паузу может только governance authority (`resume_registry`) — намеренная асимметрия: остановить проще, чем возобновить.

### UC-16. Открыть и закрыть инцидент

**Актор:** роль с `PERM_REPORT_INCIDENT` (open), governance authority (resolve).

**Результат:** on-chain `IncidentOpened` / `IncidentResolved` попадают в event-backed индекс; сертификаты покрытых batch-ей проверяются как `DISPUTED`, пока инцидент открыт.

### UC-17. Прогнать guarded live-devnet smoke перед показом

**Актор:** владелец демо. **Инструмент:** native Playwright live config с отдельным подтверждением и заранее заданным QR URL.

**Результат:** доказательство, что публичный путь `QR → finalized anchor → VERIFIED` работает на реальном devnet, и что подменённый QR hash отклоняется. Ключ оператора в браузер не попадает даже в этом прогоне.

### UC-18. Сбросить фикстуру

**Актор:** владелец демо. **Инструмент:** `./deploy/devnet-demo/native restart`.

**Результат:** native MVP перезапускается командой `./deploy/devnet-demo/native restart`; синтетические fixture-данные и чужие локальные процессы не затрагиваются.

## 5. Восстановление (Gate E0, вне MVP)

### UC-19. Восстановить реестр из зашифрованного снимка

**Актор:** три из пяти держателей долей + `chief_admin` для отдельного разрешения.

**Шаги:** снимок шифруется уникальным DEK, DEK оборачивается KEK, KEK разделён на 5 долей по схеме Шамира; шифротекст лежит у независимых хранителей; при восстановлении три masked-доли собирают KEK, `chief_admin` отдельно подписывает `Approve restore`, KEK распаковывает DEK, chunk-и расшифровываются fail-closed.

**Критерий успеха:** после восстановления пересчитанные canonical records и `merkleRoot` совпадают с якорем, уже опубликованным в Solana. Совпадение — доказательство, что восстановлено именно то состояние, а не «просто работающая БД».

**Граница:** будущая локальная Recovery Lab проверяет корректность протокола, но не заменяет реальный restore drill: процессы на одном хосте — это не независимые дата-центры.

## 6. Backup-панель (MVP)

### UC-20. Просмотреть BackupCenter-ы

**Актор:** `operator`, `auditor` или `chief_admin`. **Экран:** `/admin/backups`.

**Результат:** сайт показывает пять стартовых центров, количество папок, health, последний snapshot, статус реплики и `MerkleRoot`. `auditor` и `chief_admin` видят те же данные read-only, если не выполняют свои разрешённые действия.

### UC-21. Создать новый BackupCenter

**Актор:** `operator`. **Экран:** `/admin/backups`.

**Шаги:** нажать `Создать backup center` → система создаёт новый локальный MinIO-backed center с отдельным volume и credential → новый центр появляется со статусом `EMPTY`.

**Граница:** production-регистрация существующего внешнего хранилища не входит в MVP; это следующий адаптер.

### UC-22. Обновить копии

**Актор:** `operator`. **Экран:** `/admin/backups`.

**Шаги:** нажать `Обновить копии` → создать новый полный `SnapshotPackageV1` → отправить одну и ту же immutable-папку во все активные центры → перепроверить `ciphertextHash` и статус каждой реплики.

**Результат:** старые папки не изменяются; по каждому центру виден `COPIED`, `PENDING_RETRY` или ошибка. В каждом центре хранится максимум 12 папок; при переполнении удаляется старейшая не-`FINALIZED`, а единственная `FINALIZED` версия сохраняется.

### UC-23. Восстановить выбранный backup

**Актор:** `operator` + `chief_admin`. **Экран:** `/admin/backups`.

**Шаги:** оператор выбирает центр и папку → вставляет три masked-доли из пяти → сайт автоматически выбирает самый новый `FINALIZED` anchor без открытого incident → проверяет hashes и `MerkleRoot` → `chief_admin` нажимает `Approve restore` → полный state восстанавливается в локальный target.

**Отказы:** две доли не восстанавливают KEK; root mismatch, повреждённый ciphertext, открытый incident или отсутствие finalized anchor останавливают операцию fail-closed. Shares не сохраняются в браузере, БД и logs.

### UC-24. Проверить историю копий

**Актор:** `auditor`. **Экран:** `/admin/backups`.

**Результат:** аудитор видит создание centers, snapshot IDs, per-center copy status, retention decisions, root checks и restore outcomes, но не может создать копию, удалить папку или подписать восстановление.

## 7. Что сценариями не покрыто

Массовая выдача сертификатов, мобильное приложение, локализация интерфейса, внешний IdP и production SSO/RBAC, OCR и парсинг PDF, интеграция с реальным реестром, mainnet, production-регистрация внешних backup-систем, географически независимые custodians, hardware key custody и настоящий restore drill. Эти пункты вне scope MVP (§5.4) и не должны демонстрироваться как существующие.
