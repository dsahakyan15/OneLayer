# ADR-0002. Схема выделения `DailyAnchorLedger`: сегменты вместо единого дневного аккаунта

**Дата:** 2026-07-31
**Статус:** принято
**Задача:** `OL-A-04` (Gate A), §8.2 плана
**Артефакт:** `onchain/programs/alloc-spike`, `onchain/tests/alloc-spike.ts`

## Измерение

Локальный валидатор (agave 3.1.10, anchor-lang 1.1.2). Каждый случай —
попытка `init` PDA через CPI к system program с заданным `space`.

| capacity | space, байт | Результат |
|---:|---:|---|
| 46 | 10 040 | **успех**, rent-exempt 0.0708 SOL |
| 47 | 10 256 | отказ: `Failed to reallocate account data` |
| 48 | 10 472 | отказ |
| 96 | 20 840 | отказ |
| 192 | 41 576 | отказ |

Вариант B (`init` 10 240 → `grow`): успех за **2** вызова,
путь `10240 → 20480 → 20840`.

## Результат

**Прямой `init` ограничен 10 240 байтами**, включая создание аккаунта через
CPI. `MAX_PERMITTED_DATA_INCREASE` применяется и к первичному выделению, а не
только к последующему `realloc`.

Максимальная capacity при прямом `init`:
`floor((10240 − 104) / 216) = 46` entries.

**Это опровергает предположение §8.2 плана.** План называл вариант C
предпочтительным, потому что при нём «нет realloc-логики». Но полудневной
ledger — 10 472 байта, и прямым `init` он **не выделяется**. Вариант C в
формулировке плана нереализуем.

## Решение

Принимается **вариант C′ — сегментированный ledger с capacity 46**.

```text
seed: ["ledger", config, day_utc, u16_le(segment_index)]
capacity: 46 entries, space 10 040 байт
```

`publish_anchor` пишет в активный сегмент; при заполнении создаётся
следующий. Три сегмента покрывают 138 entries в сутки — запас к целевым 96
без отдельного механизма backlog.

## Обоснование против варианта B

| | B: `init` 10 240 + `grow` | C′: сегменты по 46 |
|---|---|---|
| Инструкций в ABI | +1 (`grow`) | 0 |
| Промежуточные состояния | ledger существует, но недоращен | нет: аккаунт создан целиком или не создан |
| Новый инвариант `publish_anchor` | «ledger доращен до полного размера» | «сегмент не заполнен» — уже есть как проверка места |
| Rent за сутки (96 entries) | 0.1459 SOL | 0.1492 SOL (3 сегмента) |
| Отказ посреди операции | ledger в промежуточном размере, нужен recovery-путь | следующая попытка создаёт сегмент заново |

Разница в rent — 0.0033 SOL в сутки (≈ 1.2 SOL в год): 128 байт накладных
на сегмент. Это цена за отсутствие класса состояний «частично выделенный
ledger», в котором `publish_anchor` обязан отказывать, а оператор — иметь
процедуру доращивания.

Вариант B остаётся работающим и проверен: если после `OL-A-02` окажется,
что суточный объём требует единого аккаунта (например, для одного чтения
PDA при верификации), переход к B не требует изменения формата entries.

## Следствия

* `spec/onchain-state-v1.md` (Gate B) фиксирует seed сегмента с
  `segment_index` и `capacity = 46`.
* Верификация читает **сегмент**, а не дневной ledger: адресация в
  сертификате должна включать `segment_index`. Это входит в
  `spec/certificate-package-v1.md`.
* `seal_daily_ledger` запечатывает все сегменты дня; `entries_hash`
  считается по сегментам в порядке `segment_index`.
* Пересчёт §8.2 плана: строка «capacity 96 → 20 840 байт → 0.1459 SOL» к
  реализации больше не относится.
* `OL-DEC-04` (модель хранения A/B/C) сохраняется: измерение касается
  выделения, а не решения о том, храним ли entries вечно.

## Границы измерения

Локальный валидатор, одна версия runtime. Лимит
`MAX_PERMITTED_DATA_INCREASE` — параметр runtime и может измениться
feature-gate. Перед mainnet go-live измерение повторяется на актуальной
версии валидатора; результат — вход в release gate 4.

Spike в продукт не переносится: авторизации, инвариантов `publish_anchor`
и реального zero-copy layout в нём нет.
