# OneLayer: назначение, принцип работы и технологии

## Границы текущей реализации — 2026-10-02

Ниже описаны принципы и legacy MVP. Полнофункциональный launcher не готов; подтверждение актуальности CURRENT и настоящий restore target отсутствуют. [Актуальная матрица реализации](implementation-status-2026-10-02.md) отделяет работающие срезы от оставшихся функций.

**OneLayer** помогает проверить записи реестра и восстановить сохранённые данные. Этот обзор объясняет текущую реализацию по коду и документации проекта.

## Что это за проект

**OneLayer** помогает обнаружить подмену опубликованных данных реестра. Для этого система выдаёт сертификаты — подписанные пакеты данных с доказательствами для проверки.

Сейчас проект реализован как MVP — минимальная рабочая версия для демонстрации на примере земельного реестра. Запись может содержать кадастровый номер, адрес участка, площадь, категорию земли, вид права и другие поля, разрешённые схемой `land-registry-v1`.

Сотрудник может проверить, совпадает ли документ с ранее опубликованной версией записи. Проверка опирается на криптографические доказательства — математические проверки данных и цифровых подписей.

Демонстрация использует искусственные данные и **Solana devnet** — тестовую сеть блокчейна. Блокчейн здесь служит общим журналом подтверждённых публикаций.

## Какие проблемы решает

**Проверка сертификата** помогает обнаружить подмену и понять, к какой версии записи относится документ.

| Проблема | Как помогает OneLayer |
| --- | --- |
| Данные документа могут изменить после публикации | Проверка обнаружит несовпадение с доказательством в блокчейне. |
| Для проверки выписки приходится доверять только серверу, который её выдал | Отдельный сервис проверки проверяет подпись издателя, доказательства и подтверждённую запись в Solana. |
| Старую версию записи можно принять за актуальную | Версии записей и состояние сертификатов учитываются отдельно; проверка различает исторические и заменённые документы. |
| Подлинный документ может относиться к спорной публикации | Система проверяет список инцидентов — зарегистрированных проблем с публикациями. Если список недоступен или устарел, результат содержит предупреждение. |
| При выдаче документа требуется раскрыть только часть сведений | Протокол поддерживает как полное раскрытие разрешённых полей, так и выборочное раскрытие с доказательствами. |
| Рабочие данные могут быть потеряны | Предусмотрены зашифрованные резервные копии и восстановление с участием нескольких держателей долей ключа. |

Проверка подтверждает совпадение с опубликованной версией. Если ошибка попала в данные до публикации, система зафиксирует и её. Достоверность исходных документов должны проверять сотрудники.

## Как работает основной сценарий

**Основной сценарий** превращает запись реестра в сертификат, который можно проверить по QR-коду.

### 1. Сотрудник вносит данные

**Веб-интерфейс** позволяет внести запись или загрузить файл. Поддерживаются JSON — текстовый формат данных — и CSV — таблица в текстовом файле.

Сервер проверяет запись по схеме `land-registry-v1`. Схема задаёт правила:

- какие поля разрешены;
- какие значения обязательны;
- в каком формате нужно передать каждое значение.

Неизвестные поля отклоняются. Это защищает от незаметной потери данных при обработке.

### 2. Система приводит данные к единому представлению

**Канонизация** приводит данные к единому виду, чтобы одинаковые записи давали одинаковый результат проверки.

- Unicode NFC приводит равнозначные способы записи символов к одной форме.
- Правила чисел задают точный формат, например число знаков после запятой.
- CBOR переводит данные в двоичный формат. Проект задаёт единый порядок кодирования.

### 3. Строятся доказательства

**Хэш** — короткий цифровой отпечаток данных, который позволяет обнаружить их изменение. Для каждого поля система вычисляет такой отпечаток из имени, значения и секретной добавки — соли.

**Дерево Merkle** объединяет отпечатки попарно, пока не останется один общий отпечаток — корень. Сначала строится дерево полей одной записи, затем дерево пакета записей, который называется batch.

- `merkleRoot` — итоговый отпечаток пакета записей.
- Merkle proof — небольшой набор данных для проверки того, что запись входит в пакет.
- Для такой проверки не нужно загружать остальные записи пакета.

### 4. Пакет фиксируется в Solana

**Anchor** — запись в блокчейне, с которой затем сверяют доказательства. Она содержит корень Merkle, отпечаток описания пакета — манифеста — и служебные данные.

Оператор просматривает транзакцию — запрос на запись в Solana — и подписывает её кошельком. Программа в Solana проверяет полномочия и публикует Anchor.

Система дожидается состояния `FINALIZED`. Только после окончательного подтверждения публикации выдаётся сертификат.

### 5. Выдаётся сертификат с QR-кодом

**Certificate Package** — пакет сертификата с данными и доказательствами для проверки. Он содержит выбранные поля версии записи, ссылку на Anchor и цифровую подпись издателя.

QR-код связывает адрес получения сертификата с его идентификатором и хэшем. Сами данные записи находятся в пакете сертификата вне блокчейна.

### 6. Отдельный сервис проверяет сертификат

**Verifier** — отдельный сервис, который проверяет сертификат. Сотрудник запускает проверку через внутреннюю страницу или QR-код.

Сервис проверяет:

- соответствует ли пакет QR-коду;
- верна ли подпись издателя;
- совпадают ли доказательства полей и записи;
- подтверждён ли Anchor в Solana;
- работает ли реестр и есть ли инциденты;
- актуальны ли версия записи и сертификат.

Результат показывает успешную проверку, старую или заменённую версию, спорную публикацию либо ошибку. Если состояние инцидентов проверить нельзя, система сообщает об этом отдельно. При паузе реестра выдача и проверка через QR блокируются.

## Где находятся данные

**Данные реестра** хранятся вне блокчейна, а **Solana** хранит доказательства для сверки. **Snapshot** — резервная копия состояния системы на определённый момент.

| Место | Что хранится |
| --- | --- |
| PostgreSQL и внутренние хранилища приложения | Рабочие записи и версии, сертификаты, доказательства, сведения об операциях и резервных копиях. |
| Solana | Anchor: корни Merkle, хэши манифестов и служебное состояние; также конфигурация реестра, полномочия операторов и инциденты. |
| Backup Centers | Зашифрованные snapshots рабочего состояния OneLayer. |

Полные поля земельного реестра не публикуются в Solana. Блокчейн служит независимой точкой сверки криптографических доказательств. Восстановить содержимое сертификата только по корню Merkle нельзя: для этого нужен сохранённый пакет или резервная копия.

## Как устроены резервные копии

**Snapshot** сохраняет рабочее состояние OneLayer для восстановления. В него входят записи, версии, сертификаты, сведения о QR-кодах, доказательства и история операций.

**AES-256-GCM** шифрует копию и позволяет обнаружить повреждение зашифрованных данных. Ключ копии защищается отдельным ключом, который делится на пять долей.

**Схема Шамира «3 из 5»** позволяет собрать ключ из любых трёх долей. Двух долей недостаточно.

MVP предусматривает пять начальных локальных центров хранения и возможность добавлять следующие. Центр хранения и держатель доли ключа — разные понятия: наличие файла резервной копии не означает наличие возможности расшифровать его.

Правила хранения и восстановления:

- Каждый центр хранит до 12 snapshots и сохраняет хотя бы одну подтверждённую копию.
- Перед восстановлением корень сверяется с выбранным окончательно подтверждённым Anchor без открытого инцидента.
- Главный администратор (`chief_admin`) отдельно подписывает разрешение на конкретную копию, её корень и цель восстановления.

Это демонстрация ограниченного контура восстановления. Локальные центры на одном компьютере не обеспечивают географическую независимость; полноценное аварийное восстановление производственной системы требует отдельной инфраструктуры и проверок.

## На чём написан проект

**TypeScript и Rust** — основные языки проекта: на них написаны приложение и программа Solana.

- SQL описывает таблицы базы данных и изменения их структуры.
- CSS задаёт внешний вид страниц.
- Bash и JavaScript используются в сценариях запуска и вспомогательных утилитах.

Версии ниже указаны по манифестам зависимостей репозитория.

| Часть проекта | Технологии | Назначение |
| --- | --- | --- |
| Веб-интерфейс | TypeScript, React 19.2.8, Next.js 16.2.12, CSS | Страницы администратора, работа с записями, публикация, сертификаты, проверка и резервные копии. |
| Admin API | TypeScript, Node.js, встроенный `node:http` | Серверные операции, сессии, роли, подготовка транзакций, выдача сертификатов и управление копиями. |
| Сервис проверки | TypeScript, Node.js | Проверка пакета сертификата и его связи с состоянием Solana. |
| База данных | PostgreSQL, SQL; библиотеки `pg` и `postgres` | Хранение рабочего состояния; доступ из TypeScript и Rust. |
| Программа в блокчейне | Rust, Anchor (`anchor-lang` 1.1.2), Solana devnet | Публикация Anchor, управление правами, пауза реестра и учёт инцидентов. |
| Клиент Solana | `@solana/kit` 7.0.0, Codama | Обращение к Solana и генерация клиента по описанию интерфейса программы — IDL. |
| Подключение кошелька | Wallet Standard | Подключение кошелька и подпись подготовленной транзакции. |
| Криптографическое ядро | Rust и TypeScript, SHA-256, HMAC, Ed25519, CBOR | Канонизация, хэширование, доказательства Merkle и подписи сертификатов. |
| Резервное копирование | TypeScript, `node:crypto`, AES-256-GCM, схема Шамира | Шифрование snapshots и восстановление ключа по трём долям из пяти. |
| QR-коды | `qrcode`, `jsqr` | Создание и распознавание QR-кодов. |
| Тестирование | Cargo tests, встроенный тестовый раннер Node.js, Playwright | Проверка Rust- и TypeScript-кода и пользовательских сценариев в браузере. |

**Node.js** запускает серверный код TypeScript. Admin API — интерфейс команд для администратора — и verifier используют его встроенные средства обработки веб-запросов.

**React** помогает собирать интерфейс из компонентов, а **Next.js** организует страницы и серверную часть веб-приложения. **Anchor** как фреймворк упрощает разработку программы Solana; это отдельное значение слова, отличное от записи Anchor в блокчейне.

Криптографические алгоритмы реализованы на Rust и TypeScript. Общие эталонные примеры проверяют, что обе реализации дают одинаковый результат.

## Кто пользуется системой

**OneLayer** — закрытый сайт для сотрудников реестра. Доступ должен идти с рабочих компьютеров организации через частную сеть или VPN — защищённое подключение к ней. Дополнительно проверяются вход пользователя и его права.

- `operator` выполняет повседневные операции в пределах своих полномочий, создаёт центры хранения и резервные копии.
- `auditor` просматривает данные и историю без права изменения.
- `chief_admin` отдельно разрешает восстановление.

Полномочия на операции в Solana задаются также самой программой реестра и её управляющими ключами.

Банк, нотариус или покупатель не получают прямой доступ к внутреннему сайту по QR. Проверку выполняет сотрудник реестра и передаёт результат по принятому в организации процессу. Ограничение доступа в развёрнутой системе должно обеспечиваться сетевой инфраструктурой и контролем устройств; одного интерфейса авторизации недостаточно.

## Что важно понимать о текущей версии

**Текущая версия — демонстрационный MVP**: она показывает путь от записи до проверки сертификата и работу резервных копий. Используются искусственные данные, тестовые ключи и Solana devnet.

Для реального внедрения отдельно нужны:

- интеграция с государственным реестром;
- защищённое управление ключами;
- хранилища в независимых местах;
- проверка восстановления после серьёзного сбоя;
- независимый монитор — сервис постоянного контроля данных и публикаций.
