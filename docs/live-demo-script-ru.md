# Скрипт живого демо OneLayer (7 минут)

Пошаговый сценарий для докладчика: что говорить, куда нажимать и что должно
быть на экране. Предлагаемый тайминг — **не более 7 минут**. Кнопки названы
точно так, как они подписаны в интерфейсе.

Контур: локальный synthetic-devnet демо (`deploy/devnet-demo/native start`), Solana
devnet, loopback-сервисы. Никакой seed-фразы и приватного ключа в браузер не
вводится. Пароль подключения берётся только из приватного runtime-файла
`/dev/shm/onelayer-devnet-demo/admin-credentials.json` (tmpfs, 0600) — его не
набирают, не показывают и не логируют. Ключи оператора — постоянные
разработочные ключи в `~/.local/state/onelayer-devnet-demo/keys/` (0600,
создаются идемпотентно, вне git). Демонстрация **не** даёт полномочий на
развёртывание новой программы: используется только уже развёрнутая программа
реестра.

## Подготовка (не входит в 7 минут)

```bash
./deploy/devnet-demo/native start          # PostgreSQL + demo-api + verifier + web
./deploy/devnet-demo/scripts/live-demo-seed   # только оценка готовности (read-only)
./apps/desktop/launcher                    # обычный лаунчер
```

`live-demo-seed` без флагов ничего не отправляет. Подготовка цепочки — только
по явному флагу `--prepare` (реестр, роль оператора, ограниченное пополнение
для rent/комиссий, сегмент реестра за день). Публикация резервного
сертификата — только по явному флагу `--approve-fallback`. Полезные команды:

```bash
./deploy/devnet-demo/scripts/live-demo-seed --prepare
./deploy/devnet-demo/scripts/live-demo-seed --prepare --approve-fallback
./deploy/devnet-demo/scripts/live-demo-tamper --in package.json --out tampered.json --mode area
```

## Отдельные состояния «заблокировано» — их нельзя путать

1. **Сервисы не запущены.** Карточки подключения показывают offline / «Not
   checked». Ничего не отправляется. Лечится запуском `native start`.
2. **Живой devnet без ключа governance (текущее состояние).** Сервисы
   работают, записи создаются, но подготовка и публикация останавливаются с
   кодом `GOVERNANCE_KEY_UNAVAILABLE` до какой-либо мутации цепочки. Ключ
   `4Y4pGizJm5CL789jRKYx5jeQLJ58eBBmf5UzGRFChikn` утерян безвозвратно, поэтому
   `grant_operator`/`unpause`/`initialize_registry` невыполнимы. Ничего не
   подменяется: `live-demo-seed --prepare` печатает отчёт с этим блокером и
   завершается с кодом 3, не отправляя транзакций. На экранах лаунчера это
   выглядят как честные коды ошибок (например `LEDGER_SEGMENT_MISSING`), а не
   как зелёный прогон.
3. **Демо на фикстурах (План B).** Это подделанный сервер и HMAC-подпись
   вместо реальной цепочки — для показа интерфейса. На каждом экране виден
   баннер «FIXTURE DATA — synthetic test backends, not live devnet».

## План B — демо интерфейса на фикстурах (явно помечено FIXTURE)

Если живой контур недоступен или заблокирован, интерфейс показывают на
фикстурах. Это **не живой devnet** и не подтверждение работы с реальной
цепочкой:

```bash
/usr/bin/python3 apps/desktop/lab/live_demo_screenshot_harness.py
```

Скрипт открывает настоящие GTK-экраны с баннером FIXTURE DATA, проходит тот же
сценарий и сохраняет снимки в
`~/.local/state/onelayer-devnet-demo/evidence/gtk/` (0700, вне репозитория).
Снимки с фикстур не являются evidence живого прогона.

## Ручная ротация trust policy (без автоматики)

Сид и лаунчер **не** ротируют trust policy автоматически. Если demo policy
истекла или сменился synthetic issuer, оператор делает это вручную и
недеструктивно:

1. Остановить контур (`./deploy/devnet-demo/native stop`).
2. Переместить истекший `deploy/devnet-demo/.runtime/native/verifier-trust-policy.json`
   в сторону (не удалять: файл остаётся как evidence).
3. Снова запустить `./deploy/devnet-demo/native start` — новая policy получит
   revision = принятый watermark + 1.
4. Проверить новые pins перед принятием. Файл watermark
   (`~/.local/state/onelayer-devnet-demo/verifier-trust/accepted.json`) и
   runtime-учётные данные не перезаписываются и не удаляются демо-скриптами.

До решения по ключу governance живой сценарий остаётся заблокированным — это
ожидаемое состояние, а не сбой демо.

## Семантика статусов (чего мы не утверждаем)

`VERIFIED` — проверка прошла при текущих данных; `VERIFIED_NO_INCIDENT_CHECK` —
проверка прошла без доступного индекса инцидентов и **не** приравнивается к
`VERIFIED`; `SUPERSEDED` / `DISPUTED` — запись или сертификат больше не
текущие; `INVALID` — проверка не прошла, поля не раскрываются.

Старые evidence-артефакты (фикстурные снимки, прошлые отчёты) — это история
разработки, а не подтверждение производственной готовности. Продакшен-гейты
(реальный signer/HSM, IdP/SSO, подписанный инсталлятор, аудит, восстановление
на реальных данных) не закрыты и здесь не утверждаются.
