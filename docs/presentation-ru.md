# OneLayer — материал для презентации

**Статус:** описательный документ, 2026-08-02. Нормативной силы не имеет; при расхождении побеждают `spec/` и `IMPLEMENTATION_PLAN.md`.
**Что здесь:** ролевые модели «как в жизни → как в системе», разбор потока, механика Merkle proof для QR-проверки, схема восстановления 3-из-5, сценарий показа и FAQ по неудобным вопросам.

---

## 1. Одна фраза, с которой начинать

> OneLayer не хранит кадастр и не заменяет реестр. Он делает так, что **любое изменение записи после публикации становится обнаружимым**, а держатель выписки может доказать её подлинность посторонней стороне без доступа к базе реестра.

Вторая фраза, сразу после первой, чтобы снять главное возражение:

> В блокчейн не попадает ни одного персонального данного. Туда попадает один хэш на пачку записей — 32 байта, из которых нельзя восстановить содержимое.

## 2. Ролевые модели: как в жизни → как в системе

### 2.1. Глава кадастра (governance authority)

**В жизни:** утверждает регламент, назначает и снимает сотрудников с правом публикации, принимает решение по спорной ситуации, отвечает за реестр перед государством.

**В системе:** это отдельный ключ — `governance_authority` в аккаунте `RegistryConfig`. Он не публикует записи каждый день. Он подписывает только редкие управляющие транзакции:

| Действие в жизни | Инструкция в программе | Что проверяет программа |
|---|---|---|
| назначить сотрудника, который вправе публиковать | `grant_operator` | подпись governance authority; создаётся `OperatorRole` с битами прав и сроком |
| снять сотрудника | `revoke_operator` | подпись governance authority; роль помечается отозванной |
| закрыть инцидент после разбирательства | `resolve_incident` | подпись governance authority; инцидент принадлежит этому реестру |
| возобновить работу после остановки | `resume_registry` | подпись governance authority |
| сменить сам управляющий ключ | `rotate_governance` | подписи **обеих** сторон — старого и нового ключа |

Важная деталь для вопроса «а если руководитель уволился или ключ украли»: смена управляющего ключа требует подписи и старого, и нового ключа, а в production (Gate E) на месте одного ключа стоит мультисиг с timelock — то есть несколько человек и обязательная задержка перед вступлением изменения в силу.

**Асимметрия остановки.** Приостановить реестр (`pause_registry`) может **дежурный по безопасности** (`emergency_authority`) — быстро, в одиночку. Снять паузу может только глава (`resume_registry`). Остановить проще, чем возобновить: это осознанное свойство, а не недоработка.

### 2.2. Сотрудник реестра (operator)

**В жизни:** вносит изменение по заявлению, формирует выписку, выдаёт её на руки.

**В системе:** роль `operator` с правом `PERM_PUBLISH_ANCHOR`. Его рабочий цикл: внести или импортировать данные → посмотреть каноническое представление → подготовить batch → **прочитать транзакцию** → подписать кошельком → дождаться finalized → выдать сертификат с нужным объёмом раскрытия.

Ключевой момент для демонстрации: перед подписью система показывает всё, что уйдёт в сеть — кластер, программу, все аккаунты с флагами, корень, предыдущий якорь, комиссию, логи симуляции. Кошелёк подписывает **ровно те байты**, что были показаны, и сервер повторно проверяет соответствие подписанной транзакции сохранённому намерению перед отправкой.

### 2.3. Ревизор (auditor)

**В жизни:** проверяет, кто и что делал, но сам ничего не меняет.

**В системе:** роль `auditor`. Она ограничена на уровне API, а не скрытием кнопок: даже прямой запрос к `/v1/admin/records` из консоли браузера вернёт `403 ROLE_FORBIDDEN`. Это стоит показать вживую — эффект сильнее, чем слайд.

### 2.4. Проверяющий: нотариус, банк, покупатель

**В жизни:** получил бумажную выписку и должен понять, настоящая ли она; звонит в реестр, ждёт ответ, верит на слово.

**В системе:** сканирует QR. Проверка идёт против Solana, а не против сервера реестра. Ответ — один из шести статусов, каждый со своим объяснением. Зелёный `VERIFIED` выдаётся только когда сошлось всё, включая доказанную свежесть индекса инцидентов.

### 2.5. Независимый монитор (Gate D, вне MVP)

**В жизни:** служба внутреннего контроля, которая не подчиняется тому, кого проверяет.

**В системе:** отдельный процесс с отдельными учётными данными, отдельной репликой источника и **второй, независимой реализацией** криптографии (TypeScript против Rust в основном контуре). Смысл: если в основной реализации ошибка, монитор, написанный по спецификации, а не по коду pipeline, эту ошибку увидит. Общая библиотека дала бы одинаково неверный результат в обоих контурах и не обнаружила бы ничего.

## 3. Как работает приложение: поток целиком

```
сертификат пользователя (JSON/CSV)
   ↓ валидация по схеме реестра land-registry-v1
каноническая запись: поля → deterministic CBOR (RFC 8949), NFC, decimal строкой
   ↓ на каждое поле: field_commitment = SHA256(домен ‖ путь ‖ значение ‖ секретная соль поля)
field-дерево записи → fieldRoot
   ↓ record_commitment = SHA256(домен ‖ registry ‖ id-обязательство ‖ версия ‖ fieldRoot)
batch-дерево по всем записям → merkleRoot
   ↓ манифест пачки → manifestHash
одна транзакция Solana: publish_anchor(merkleRoot, manifestHash, previousAnchorHash, …)
   ↓ finalized
сертификат: раскрытые значения + их соли + Merkle proof + ссылка на якорь + подпись издателя
   ↓
QR: URL ‖ certificateId ‖ certificateHash
```

Что стоит проговорить отдельно:

- **Соль на каждое поле.** Без соли хэш поля `status = ACTIVE` перебирался бы за миллисекунды: множество значений мало. Соль выводится HMAC-ом из случайного ключа версии записи, который не покидает сервер и не отдаётся ни одним API. Поэтому раскрытие одной соли не помогает восстановить остальные.
- **Одна транзакция на пачку.** Стоимость не растёт с числом записей в пачке: в сеть уходит один корень.
- **Сертификат не якорится.** В цепочке нет `certificateHash`. Сертификат привязан к якорю подписью издателя и Merkle proof — второй протокол не создаётся.
- **Цепочка якорей.** Каждый якорь содержит хэш предыдущего. Удалить одну публикацию из середины истории, не сломав цепочку, нельзя.

## 4. Merkle proof: как QR-проверка доказывает подлинность

Это главный технический момент презентации. Объяснение на четырёх записях.

**Шаг 1. Каждая запись сворачивается в одно 32-байтовое обязательство.**

```
запись A → leaf_A = SHA256(0x00 ‖ record_commitment_A)
запись B → leaf_B
запись C → leaf_C
запись D → leaf_D
```

**Шаг 2. Листья попарно хэшируются вверх (RFC 6962).**

```
        merkleRoot
        /        \
     H_AB        H_CD
     /  \        /  \
 leaf_A leaf_B leaf_C leaf_D
```

`H_AB = SHA256(0x01 ‖ leaf_A ‖ leaf_B)`. Префиксы `0x00` и `0x01` разделяют листья и узлы: без них можно было бы выдать внутренний узел за лист.

**Шаг 3. В Solana уходит только `merkleRoot` — 32 байта.** Ни одной записи, ни одного значения.

**Шаг 4. Сертификат для записи C содержит путь до корня — «Merkle proof».**

```
proof(C) = [ leaf_D (справа), H_AB (слева) ]
```

Два хэша. Для 1000 записей путь — 10 хэшей, для миллиона — 20: длина растёт логарифмом.

**Шаг 5. Что делает проверяющий после сканирования QR.**

1. Из QR берётся `certificateId` и `certificateHash`. Сервер отдаёт пакет; если хэш пакета не совпал с хэшем из QR — отказ **до** любого обращения к цепочке. Подменить пакет, оставив старый QR, нельзя.
2. Проверяется подпись издателя на пакете.
3. Из раскрытых значений и их солей пересчитывается `field_commitment` каждого поля и собирается `fieldRoot`. Если хоть одно значение подправлено — корень не сойдётся.
4. Из `fieldRoot`, идентификатора и версии собирается `record_commitment`, из него — лист, и по proof-у поднимается корень: `SHA256(0x01 ‖ H_AB ‖ SHA256(0x01 ‖ leaf_C ‖ leaf_D))`.
5. Полученный корень сравнивается с корнем, который лежит в **finalized** транзакции Solana, в том самом аккаунте, который назван в сертификате. Проверяются владелец аккаунта, длина и дискриминатор — данные RPC считаются недоверенными.
6. Отдельно проверяется, что batch не покрыт открытым инцидентом, и что индекс инцидентов доказал свою свежесть.

Совпало всё — `VERIFIED`. Не совпал корень — `INVALID`. Не доказана полнота индекса — `VERIFIED_NO_INCIDENT_CHECK`, и это **не** зелёный результат.

**Частичное раскрытие.** Если оператор раскрыл только два поля из четырёх, пакет несёт значения, соли и field proof только этих двух. Проверяющий пересчитывает `fieldRoot` из них по тем же правилам — корень тот же, якорь тот же, статус тот же `VERIFIED`. Банк видит площадь и статус и не видит правообладателя, при этом уверен, что видит именно анкоренные данные.

## 5. Резервное восстановление 3-из-5

Вопрос, который задают почти всегда: «а если ваша база сгорит — блокчейн же не хранит данные?»

**Схема ключей.**

```
DEK  — уникальный ключ на каждый снимок; шифрует данные (AES-256-GCM)
KEK  — шифрует DEK
KEK  разделён по схеме Шамира на 5 долей; любые 3 восстанавливают KEK, любые 2 — нет
```

Долями владеют пять разных держателей — в production это разные люди с аппаратными идентичностями. Координатор, который создаёт снимок, **не видит ни одной доли**. Хранители шифротекста (три независимые площадки со своими учётными данными и своими томами) не имеют доступа ни к KEK, ни к долям.

**Как проходит восстановление.**

1. Снимок разбит на chunk-и; у каждого свой nonce и свой authentication tag, а в AAD входят идентификатор реестра, идентификатор и версия снимка, индекс chunk-а и общее число chunk-ов — так подмена, перестановка или усечение chunk-ов обнаруживаются.
2. Три держателя предоставляют доли; KEK собирается в чистой изолированной среде, доли попадают туда одноразовыми файлами в tmpfs.
3. KEK распаковывает DEK, DEK расшифровывает chunk-и. Любая ошибка тега — остановка **fail-closed**: частично расшифрованные данные не используются.
4. После сборки пересчитывается hash всего plaintext и сверяется с записанным.

**Главный критерий, ради которого всё это делается.** После восстановления заново вычисляются canonical records, field roots и `merkleRoot` — и сравниваются с якорем, который уже лежит в Solana. Совпало — восстановлено доказуемо то же состояние. Не совпало — учение провалено, даже если база «работает».

**Честная граница.** Контейнеры на одном хосте — это не независимые дата-центры: у них общий администратор, ядро и диск. Docker-лаборатория проверяет корректность протокола и процедуры; настоящее учение на реальной инфраструктуре — отдельное обязательное условие до запуска.

## 7. FAQ: неудобные вопросы

**«Зачем здесь блокчейн? Сделайте подписанный лог в своей базе.»**
Подписанный лог проверяет тот, кто им владеет. Если администратор реестра может переписать и данные, и лог, внешняя сторона не сможет отличить исправление от подлога. Публичная цепочка даёт время публикации и неизменность, которые не подчиняются администратору реестра. Мы используем её ровно для этого — не для хранения данных.

**«Персональные данные попадают в блокчейн?»**
Нет. В цепочку идут `merkleRoot` и `manifestHash` — 32 байта каждый — и служебные поля якоря. Значения полей и идентификаторы записи там отсутствуют. Более того, идентификатор записи в сертификате — не сам номер дела, а HMAC-обязательство к нему.

**«Хэш можно подобрать: значений `status` всего четыре.»**
Поэтому хэшируется не значение, а значение с секретной солью, выведенной из случайного ключа версии записи. Ключ не покидает сервер и не отдаётся ни одним API. Перебор без ключа не работает.

**«Что мешает вам опубликовать корень от подделанных данных?»**
Ничего — и мы этого не скрываем. Якорь доказывает неизменность **после** публикации, а не корректность до неё. Против подлога на входе работает другой механизм: независимый монитор (Gate D), который читает источник своей репликой, своими учётными данными и второй, независимой реализацией криптографии, и открывает инцидент при расхождении. Плюс требование сопоставлять изменение с подписанным событием workflow.

**«Кто-то поправил строку прямо в базе — вы это увидите?»**
Да, через пересчёт корня: он перестанет совпадать с якорем. Именно это показывает сценарий `demo incident`, и результат проверки становится `DISPUTED`. Честная граница: физическое вмешательство в файлы БД в обход журнала реплика может не увидеть — для этого нужен независимый канал к первичной базе или storage-level attestation, и в плане это записано как открытый риск, а не как решённая задача.

**«Solana упадёт или подорожает — что тогда?»**
Комиссия — доли цента за пачку; аренда аккаунтов рассчитана и записана в плане. Если сеть недоступна, публикация уходит в durable-очередь и повторяется; попытка с неизвестным исходом **опрашивается по известной подписи**, а не пересобирается — иначе можно опубликовать одно и то же дважды. Формат якоря от сети не зависит: он привязан к нормативному preimage, а не к деталям хранения.

**«Почему devnet, а не mainnet?»**
Потому что это демонстрация на синтетических данных и тестовых ключах. Выход на mainnet требует внешнего аудита программы, пентеста, юридического заключения и учения по восстановлению — это отдельные обязательные gate-ы, и обходить их ради красивой демонстрации нельзя.

**«Что если у вас украдут ключ оператора?»**
Ключ оператора умеет только публиковать якоря — он не может выдавать роли, менять управляющий ключ или обновлять программу. Украденный ключ отзывается транзакцией `revoke_operator`, а опубликованные им якоря остаются в истории и разбираются через механизм инцидентов. В production ключи живут в HSM, а governance — мультисиг с timelock.

**«Зелёная галочка — это гарантия?»**
Это утверждение: «данные совпадают с тем, что было опубликовано в такой-то момент, и на этот batch нет открытого инцидента». Если полноту проверки инцидентов доказать не удалось, статус не зелёный, а `VERIFIED_NO_INCIDENT_CHECK`. Если появилась более новая версия записи — `VERIFIED_HISTORICAL`. Мы намеренно не сводим всё к «да/нет».

**«Сколько это стоит в эксплуатации?»**
Одна транзакция на пачку плюс аренда аккаунтов реестра. Сегмент журнала на 46 записей — около 0.071 SOL rent-exempt, три сегмента покрывают сутки при целевой нагрузке. Расчёт и варианты хранения (полные записи навсегда, только rolling digest, горячее окно 90 дней) описаны в плане; выбор — решение владельца до запуска.

**«Почему нельзя просто проверить всё офлайн, без вашего сервера?»**
Криптографию — можно: подпись, соли, оба Merkle proof и сверка с цепочкой не требуют нашего сервера. Что требует индекса — это ответ на вопрос «нет ли сейчас открытого инцидента по этой пачке»: перечислить инциденты по диапазону batch-ей средствами самой программы нельзя. Поэтому индекс обязан публиковать watermark, а верификатор берёт голову цепочки **сам** — иначе зависший индекс объявлял бы устаревшие данные актуальными.

## 8. Чего не обещать со сцены

- что система проверяет **истинность** данных реестра;
- что демонстрационный логин — это контроль доступа (production SSO и RBAC — Gate E);
- что восстановление 3-из-5 уже прошло боевое учение;
- что мониторинг (независимый контур) уже работает — это Gate D;
- что сканирование с телефона по локальному адресу заработает без отдельного HTTPS-стенда.
